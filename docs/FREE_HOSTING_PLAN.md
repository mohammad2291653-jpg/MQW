The reviewed template is `supabase/runtime/schema.sql`; it represents CLI-generated migrations `supabase/migrations/20261118155145_runtime_private_store.sql` and `supabase/migrations/20261118155344_voice_ownership_index.sql`. The older normalized proposal has moved to `supabase/proposals/normalized_schema.sql` and is not an active migration. There are seven compatibility tables: users, sessions, records, setup_tokens, idempotency, file_cleanup, and voice_blobs. Stable event IDs, original timestamps, content versions and historical private snapshots must survive any existing-data import.

Private voice files are stored as bounded PostgreSQL `bytea` rows with an ownership foreign key to their metadata. This keeps audio and metadata within the same durable transaction and deletion cascade, without another storage service. The existing 20 MiB per-file and 200 MiB per-account application quotas still apply. **Audio counts against the 500 MB database allowance**, not Supabase's separate 1 GB Storage allowance. Do not claim the selected runtime uses a Supabase Storage bucket.

Use the shared IPv4 **Session Pooler on port 5432** for the persistent Node service. The owner supplied the actual Connect hostname, `aws-1-eu-central-1.pooler.supabase.com`; it was not inferred from region. A custom-role connection uses the username `mqw_app.<PROJECT-REF>`. For future projects, obtain the actual host from Connect or authenticated Management API `GET /v1/projects/<ref>/config/database/pooler`; cluster indices can vary. Do not select the paid IPv4 add-on or dedicated paid pooler. Require TLS verification and keep the full connection string server-only.

The runtime role is created NOLOGIN/NOBYPASSRLS, without administrative privileges. The operator privately assigns its login password separately. All runtime tables enable and force RLS. Owner records, idempotency receipts and audio are constrained by transaction-local `mqw.user_id` established from the verified opaque session. Auth/session/setup/cleanup tables permit only the trusted backend role's pre-authentication operations. This is the actual custom-cookie access model; it does not use `auth.uid()` or Supabase JWTs. PUBLIC, anon, authenticated and service_role receive no private-schema/table access.

The repository acquires one PostgreSQL client, begins a transaction, establishes verified owner context with transaction-local `set_config`, serializes transitions with a transaction-scoped advisory lock, awaits operations, and commits or rolls back before releasing the client. Local SQLite operations also serialize awaited callbacks. Set `MQW_STORAGE_BACKEND=postgres` explicitly on the free host so a missing database secret fails closed instead of silently falling back to ephemeral SQLite. `MQW_DATABASE_URL` remains a server-only secret, with verified TLS and an optional configured CA certificate.
